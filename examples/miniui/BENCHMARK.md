# miniui: Pystachy, CPython and Cython performance

This experiment measures the optional miniui prototype from
[PR #1116 at `f8a6a5a0`](https://github.com/den-run-ai/pystachy/tree/f8a6a5a0918216555dca6e652791c861fbcacd87/examples/miniui).
It separates Python-side computation and drawing submission from real raylib
rendering. The widget core, Python renderer and production C adapter are
unchanged. Reproducible inputs, build identities, samples and validation are
retained with the [November 6, 2026 results](results/2026-11-06/).

**Yes: Pystachy substantially reduces the Python-side CPU work.** At the default
150 particles, its AOT CPU frame is **28.4× faster than CPython with a direct
native binding and 5.9× faster than the explicitly typed Cython port**.
The complete small scene takes about 2 ms with either Pystachy or typed Cython;
rendering dominates there. At 15,000 particles, real AOT frame time improves
**2.76× over native-binding CPython and 1.35× over typed Cython** on this
software-rendered host. These are ratios of measured medians, not universal
language-speed constants. The study and harness were prepared with ChatGPT assistance.

## Results

Lower time is better. Entries are medians of seven independent processes;
dispersion and individual samples belong in the linked result files. These are
steady execution times, excluding compilation, imports and window creation.

| Implementation | CPU frame, 150 particles (µs) | Real frame, 150 particles (ms) |
| --- | ---: | ---: |
| CPython, unchanged FFI twin | 1,427.41 | 3.502 |
| CPython, direct native binding | 171.77 | 2.180 |
| Cython, unchanged source | 1,495.12 | 3.589 |
| Cython, direct native binding | 180.72 | 2.232 |
| Cython, typed classes/direct binding | 35.58 | 2.030 |
| Pystachy AOT | 6.04 | 1.944 |
| Pystachy JIT | 8.28 | 1.896 |

### Where CPU time goes

These phases are timed independently; their medians need not sum to the fused
complete-frame median. All entries are microseconds at 150 particles.

| Phase | CPython native binding | Typed Cython | Pystachy AOT |
| --- | ---: | ---: | ---: |
| Simulation | 8.37 | 2.22 | 0.56 |
| UI/command construction | 94.74 | 31.12 | 4.71 |
| Prebuilt-command submission, stub | 78.85 | 2.52 | 1.08 |
| Idle input snapshot | 0.76 | 0.20 | 0.06 |

The raw scalar-rectangle loop is effectively tied: **2.73 ns/iteration for
Pystachy AOT and 2.57 ns for typed Cython**. This tiny loop includes its loop
arithmetic and the stub's counter. It provides no evidence that Pystachy makes
the underlying C call intrinsically faster. Its larger frame advantage comes
from the surrounding code, representations and object construction.

### Scaling the same particle scene

The number of controls stays fixed; these are particle-count measurements,
not thousands of interactive widgets. Times below are milliseconds.

| Workload | CPython native binding | Typed Cython | Pystachy AOT |
| --- | ---: | ---: | ---: |
| CPU frame, 1,500 particles | 1.562 | 0.290 | 0.042 |
| CPU frame, 15,000 particles | 21.235 | 3.110 | 0.429 |
| Real frame, 1,500 particles | 4.565 | 3.417 | 3.133 |
| Real frame, 15,000 particles | 34.180 | 16.731 | 12.388 |

The default real-scene difference against typed Cython is inconclusive: its
middle 50% of samples spans **1.920–2.245 ms**, versus **1.838–1.973 ms** for AOT.
The direct CPython binding shows a more consistent but modest difference:
**2.180 → 1.944 ms**, about 11% less time. At 15,000 particles the real-scene
IQRs are **32.437–35.654 ms** for CPython, **15.904–17.941 ms** for typed Cython
and **11.836–12.903 ms** for AOT. One AOT sample was 16.83 ms, so this is not a
guarantee that every frame meets a deadline. Each sample is itself a batch
average. The [summary](results/2026-11-06/summary.json) retains medians, IQRs,
minima and maxima for every case.

The prebuilt-command real-render test also approaches the common renderer
cost: at 150 particles its medians are 1.98 ms for native-binding CPython,
1.97 ms for typed Cython and 2.10 ms for AOT. There is no universal rendering
win. All variants already include the PR's clipping/batching improvements.

## What each implementation measures

Every variant calls the same scalar C adapter and the same selected native
library. The comparisons distinguish compiler gains from binding overhead:

| Result name | Application/UI code | Native interface |
| --- | --- | --- |
| `cpython_twin` | Original Python | Repository `ffi.extern` twin using ctypes and generic argument binding |
| `cpython_native` | Original Python | Conventional CPython extension generated by Cython |
| `cython_auto` | Original `.py` compiled with default safe type inference | Original FFI twin |
| `cython_native_auto` | Original `.py` compiled with default safe type inference | Typed C calls within the compiled renderer |
| `cython_typed_noexcept` | Extension classes, typed fields/locals and C-level method calls | Direct C calls; non-raising scalar helpers declared `noexcept` |
| `pystachy_aot` | Original Python compiled ahead of time | Pystachy scalar FFI |
| `pystachy_jit` | Original Python compiled by the native JIT driver | Pystachy scalar FFI |

The twin preserves FFI semantics but performs signature binding, checks and
ctypes conversion on every call. Its result alone would overstate the advantage
over a conventional Python binding. The direct native CPython comparison
removes that particular overhead while keeping the application interpreted.

The typed Cython port preserves the algorithm and Python lists, sets and strings.
It unboxes particle reads for C `double` arithmetic, then stores boxed Python
floats back into the list. Extension-object construction and reference counting
remain. It is a useful optimized comparator, not a maximum-performance Cython
implementation. Scalar helpers that cannot raise omit exception polling; text
encoding and Python-exported argument checks retain exception handling. See the
[Cython build details](bench_cython/README.md) for exact transformations and
valid-input boundaries.

## Workloads and measurement

[`benchmark_workload.py`](benchmark_workload.py) reproduces the demo's controls
and particle arithmetic at 150, 1,500 and 15,000 particles. The window is always
760 × 520. A fixed 1/60-second simulation step and bounded iteration count
replace live delta time and window-close polling. In a complete frame, controls
are evaluated first, then particle updates and rectangle creation share one
loop, as in the demo. Input is idle; these are not typing or interaction latency
measurements.

| Phase | Work inside the timed loop |
| --- | --- |
| `simulate` | Update the numeric position list; no UI construction or drawing |
| `ui` | Rebuild controls and particle commands at fixed positions |
| `submit` | Draw a prebuilt command list repeatedly |
| `frame` | Poll input, construct controls, update particles, emit commands and draw |
| `ffi` | Submit one scalar rectangle call per iteration; no real rendering |
| `poll` | Poll the backend and construct an input snapshot |

The last two phases use the 150-particle setup only; their loop work does not
depend on particle count. Real raylib runs cover `frame` and `submit`.

The display-free library compiles the production adapter against a minimal
raylib stub. Every drawing operation updates counters; the timed build omits
argument hashing. A separate verification build hashes operation order,
coordinates, colors and text. Its synthetic text widths do not model raylib's
font or GPU costs. Counter totals are underlying raylib calls: beginning a
frame, clearing its background and ending a clip contribute separately. They
are not the renderer's scalar FFI-call count.

Each case uses seven interleaved subprocess samples pinned to CPU 0, with a
fixed shuffle seed and 30 warmup iterations per sample. Calibration chooses an
iteration count separately for each runtime, targeting 0.2 seconds for CPU
cases and 0.3 seconds for real rendering. Actual elapsed times and iteration
counts are retained. Reported cost is elapsed time divided by iterations;
startup, calibration, warmup, checksums, screenshots and teardown are excluded.
The logged whole-process wall time includes those activities and must not be
presented as a separately measured startup cost.

The real adapter disables the production 60 FPS limiter and clears the vsync
hint. Real-frame time includes the host-visible drawing and buffer-swap path;
it is not isolated GPU execution time. Builds, profiles and other benchmark
batches are kept outside measured intervals. Default garbage collection remains
enabled. No fast-math, GC disabling or special Pystachy optimization settings
are used.

## Correctness and profiling

Before timing each case, all runtimes execute the same 13 iterations after
three warmup iterations. State checks include positions, input flags/text,
control values, focus/capture/cursor and drawing-command contents. The verifying
stub also compares native call counts and an ordered argument digest. Positions
and speed are quantized to 1e-6 in the state checksum; this detects mismatches
but is not a proof of bit-identical floating-point arithmetic. Hashes are also
mismatch detectors, not collision-free proofs.

Every timed repetition must reproduce its runtime's checksum and operation
counts at its calibrated iteration count. Counts and final states naturally
differ across runtimes when their iteration counts differ. Result labels and
iteration counts must match the request, and elapsed time must be finite and
positive. Disassembly confirms that the native timed loops remain present.

The existing ten headless UI scenarios and native boundary checks exercise the
comparison builds independently of timings. Real framebuffer comparisons use
the same fixed frame count and compare decoded pixels outside measurement.
Real native counters return `-1` for unavailable instrumentation; they do not
certify the framebuffer.

Completed **980 final timed process samples** and **140 fixed-count preflight
comparisons** across the seven variants. All deterministic checks passed. The
Cython validation adds 48 workload comparisons across the CPython reference and
three final Cython modes, plus ten existing UI scenarios per runtime and
invalid-input rejection checks. Native-binding CPython also passed the ten UI
scenarios and the common benchmark checks. [Cython evidence](results/2026-11-06/cython-validation.json).

All seven final real-render variants produced identical decoded 760 × 520
pixels, with visible controls and particles. The shared pixel SHA-256 is
`cc892a6fdef1e053c1bf57cee9d9da502a8f6fb5aa5fb6e1d8e0e1bc01f502ce`.
[Pixel evidence](results/2026-11-06/pixel-validation.json) ·
[actual AOT screenshot](results/2026-11-06/pystachy-aot.png).
The native compiler was reused from the same source after re-emitting its own
IR and comparing it byte-for-byte with the prior bootstrap's stage 3.
[Source/build provenance](results/2026-11-06/provenance.json).

The separate CPython profile attributes about **86% of the generic-twin run's
instrumented cumulative time to `ffi.py`'s call wrapper**, including signature
binding and argument preparation. With the direct native binding, UI and
command construction becomes the dominant Python work. The twin is therefore
a useful same-source baseline but a poor sole comparator for an efficient
CPython extension.

Loop-scoped Callgrind collected **347,966,878 instructions for Pystachy AOT**
and **2,536,041,197 for typed Cython** over the same 5,000 frames, about **7.3×
fewer** for AOT. The Cython profile highlights object allocation/freeing,
constructor calls, tuples and integer boxing. The AOT profile concentrates on
UI creation, renderer traversal, allocation bookkeeping and list growth.
Instruction counts are not CPU cycles or wall-time percentages.

A separate default-150-particle AOT run over 50,000 timed frames reported
**35 collections, 1.6 ms in collection and a 34.0 MiB heap peak**. Whole-process
collection time was equivalent to about **0.55% of the 288.6 ms timed loop**;
allocation and initialization still cost work outside collection. This supports profiling
command-object construction and storage reuse before tuning collection
thresholds. Reuse would need explicit frame-lifetime and aliasing rules.

## Environment and limits

The host exposes an AMD EPYC 9V74 x86-64 processor, nine virtual CPUs, an
eight-CPU cgroup quota and an 8 GiB memory limit. Child processes are pinned to
CPU 0. The comparison uses CPython 3.13.16, Cython 3.1.8, setuptools 80.9.0 and
LLVM/Clang 18.1.3. Pystachy AOT uses its normal `-O2` path; Cython extensions use
`-O3`, bounds/initialization checks and ordinary GIL-held execution. Typed Cython
also checks integer overflow. The two `_auto` builds use `infer_types=None`;
the typed build supplies explicit hot types.

Real rendering uses raylib 5.5, Xvfb and Mesa llvmpipe software rendering, with
`LP_NUM_THREADS=1`, `OMP_NUM_THREADS=1` and a common display. These results do
not establish physical-GPU performance, another OS's behavior or interactive
tail latency. Shared-host noise remains possible; small differences should be
read against sample dispersion.

A native CPU saving can leave the default demo visually unchanged because its
normal target is 60 FPS. Its practical benefit is reduced CPU work and more
simulation headroom. The real-render comparison establishes how much of that
saving remains when this renderer is included. Cython C arrays/memoryviews,
object pooling, specialized constructors or batching could narrow gaps; those
are further implementations, not measured results here.

## Reproduce

Use the benchmark commit containing this harness, with its pinned prototype
sources. From the repository root, provide CPython 3.13.16 with headers, a
complete LLVM 18.1.3 toolchain, raylib 5.5 headers/library, and a working X11
display for real rendering. Pillow is needed only for pixel validation.

```sh
BENCH_PY=/path/to/python3.13
export PYSTACHY_LLVM=/path/to/llvm-18/bin
BENCH_CC="$PYSTACHY_LLVM/clang"
BENCH_RAYLIB=/path/to/raylib/src

make PY="$BENCH_PY"
"$BENCH_PY" examples/miniui/bench_native/build_native.py \
  --out build/miniui-bench/adapters --cc "$BENCH_CC" \
  --raylib-dir "$BENCH_RAYLIB"
./pystachy build examples/miniui/benchmark_entry.py \
  -o build/miniui-bench/miniui-aot

uv pip install --python "$BENCH_PY" --target build/miniui-bench-deps \
  'Cython==3.1.8' 'setuptools==80.9.0' Pillow
for mode in cpython_native same_source_auto cython_native_auto cython_typed_noexcept
do
  PYTHONPATH=build/miniui-bench-deps "$BENCH_PY" \
    examples/miniui/bench_cython/build.py \
    --output build/miniui-bench-cython \
    --library-dir build/miniui-bench/adapters/stub \
    --cc "$BENCH_CC" --mode "$mode"
done
"$BENCH_PY" examples/miniui/benchmark_manifest.py \
  --python "$BENCH_PY" --llvm "$PYSTACHY_LLVM" --standard-cython \
  --output build/miniui-bench/final-manifest.json
"$BENCH_PY" examples/miniui/bench_cython/check.py \
  --output build/miniui-bench-cython \
  --library-dir build/miniui-bench/adapters/verify \
  --modes cpython_native same_source_auto cython_native_auto cython_typed_noexcept \
  --record build/miniui-bench/cython-validation.json
```

Configure `DISPLAY` and any required X11 authorization before the next block.
Use an otherwise idle host and finish all builds first.

```sh
export LD_LIBRARY_PATH="$BENCH_RAYLIB${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"
export LIBGL_ALWAYS_SOFTWARE=1
PYTHONPATH=build/miniui-bench-deps "$BENCH_PY" \
  examples/miniui/validate_benchmarks.py \
  --manifest build/miniui-bench/final-manifest.json \
  --output-dir build/miniui-bench/screenshots --cpu 0
"$BENCH_PY" examples/miniui/run_benchmarks.py \
  --manifest build/miniui-bench/final-manifest.json --cpu 0 --rounds 7 \
  --target-seconds 0.2 --particles 150,1500,15000 \
  --output build/miniui-bench/cpu-final.json
"$BENCH_PY" examples/miniui/run_benchmarks.py \
  --manifest build/miniui-bench/final-manifest.json --cpu 0 --rounds 7 \
  --target-seconds 0.3 --particles 150,1500,15000 --real --modes frame,submit \
  --output build/miniui-bench/real-final.json
```

Use `--smoke` for a short correctness run, not a performance result. Rebuild
every comparison after changing shared source. Preserve generated build
metadata and raw samples alongside any reported summary.

For separate profiling, install Valgrind/Callgrind and then run:

```sh
"$BENCH_PY" examples/miniui/profile_benchmarks.py \
  --manifest build/miniui-bench/final-manifest.json \
  --output build/miniui-bench/profiles --valgrind /path/to/valgrind --cpu 0
```

`--valgrind-lib` supports an extracted Valgrind package. The profiler uses
cProfile for the two CPython bindings, a separate AOT GC diagnostic, and
Callgrind collection limited to each compiled benchmark loop. Do not run it
concurrently with the timing suite. Compiler/runtime verification and physical
GPU coverage are outside this benchmark-only change; nothing was merged.
