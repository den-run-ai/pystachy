## The remaining misses, by risk

### Found and fixed

- **`open()` kept alive the writer it collected to close** (`runtime.c`). `pys_open` closes an
  unreachable writer of the path it opens by a collection, which it ran from inside its search of
  the open files. The instrumented runtime's register allocation left the writer just found in
  `%r15`, which `collect()` spills and scans as a root, so the writer survived unflushed and the
  read saw an empty file: `tests/rt_list_vacated.py` failed in both tiers. The normal build keeps
  it in a caller-saved register, by chance. The search is now a leaf of its own.
- **`sys.exit()` of a tuple** (`builtins.py`). CPython raises `SystemExit(*t)`: `sys.exit((3,))`
  exits with status 3 and no output, `sys.exit(())` with status 0. Pystachy printed the tuple and
  exited with status 1, with or without `try`. A fixed-shape tuple's items are now the arguments
  (`tests/exit_optional_code.py`, `tests/exit_tuple_status.py`, which fail without the fix). A
  tuple whose length is known only at run time still prints its repr when it has one item or none.

## Second round: changed code, values and configurations

A covered line can still give a wrong result for particular values, under a combination of
optimizations or in another build of the runtime, and a total says nothing about the code that
a change adds.

### Changed code

With `COVERAGE_BASE=REF`, either summary also lists the code changed since the merge base of
`REF` and `HEAD` that no suite ran: statements and lines not run, branches not taken
([reading coverage](../testing.md#reading-coverage)). The Coverage workflow lists them for a pull
request that runs it and for a run by hand (its `base` input). Against main `727b88ce`, the run on
`655db8ac` found the compiler's 3 changed statements (`sys.exit()` of a tuple) and the runtime's
7 changed lines (`open()`'s search, now a function of its own) all run; of the 18 branches of
those lines, 2 were not taken: an open writer to another file of the same device, which the
search passes over, and `PYSTACHY_GC=off`, under which `open()` collects nothing.

### Values and table states

| Test | Reaches |
|---|---|
| `int_float_compare_edges.py` | Comparisons of an int with floats beyond the 64-bit range and next to -2\*\*63; `(-1) ** n`; `round()` to fewer than -308 and -400 digits |
| `list_bound_extremes.py` | `insert()` and `index()` bounds past either end, the 64-bit extremes included |
| `set_table_paths.py` | An insertion that passed a deleted slot takes it, in sets of ints and of strs; `pop()` wrapping past the table's end; the operand sizes at which `s -= t` and `s.difference(d)` take other ways |
| `sort_numbers_merge.py` | Long int and float sorts, galloping runs, the 64-bit and float extremes, the order of equal zeros, and NaNs, whose positions show each step of timsort |
| `memory_error_uncaught.py` | Running out of memory: what the program printed is written, stderr's last line is `MemoryError` and the status 1, as for CPython's uncaught `MemoryError` |

The first three run 5 lines and 18 branches of `runtime.c` that the run on `f96ba9e7` did not,
and no statement of the compiler. The sort test runs nothing new: the branch of the merges that
the report shows untaken is in their copy for sorts that keep an undo record, which only sorts
of items whose comparisons can raise do. It checks results instead: with a gallop threshold of 6
instead of 7, or a minrun from 32 instead of 64, it fails. `memory_error_uncaught.py` runs `oom()`,
which the first round found untested; that no `except` clause catches it is a documented
deviation ([errors and control flow](../language/compatibility.md#errors-and-control-flow)).

### Configurations

`make variants` ([configuration variants](../testing.md#configuration-variants)) runs the corpus,
JIT and AOT, in configurations that verification does not test. On `655db8ac`, in this
container (4 vCPUs):

| Variant | Setting | Checks | Time |
|---|---|---|---:|
| `opt-1` | `PYSTACHY_OPT=-moduleints,-fieldtbaa,-tupleret,-unionslots` | 4,913 passed | 573 s |
| `opt-2` | `PYSTACHY_OPT=-dictfuse,-tupleiter,-listfast,-unionslots` | 4,913 passed | 572 s |
| `opt-3` | `PYSTACHY_OPT=-listget,-tupleiter,-listfast,-fieldtbaa,-tupleret` | 4,913 passed | 573 s |
| `opt-4` | `PYSTACHY_OPT=-listget,-dictfuse,-listfast,-moduleints,-tupleret` | 4,913 passed | 584 s |
| `opt-5` | `PYSTACHY_OPT=-listget,-dictfuse,-tupleiter,-moduleints,-fieldtbaa,-unionslots` | 4,913 passed | 598 s |
| `cflags-O0` | `PYSTACHY_CFLAGS=-O0` | 4,913 passed | 209 s |

No combination of the passes changed a result, and neither did the unoptimized runtime. To see
which builds of the runtime leave a dead pointer where the collector scans, the `open()` fix was
reverted and `tests/rt_list_vacated.py` run, JIT and AOT, against builds of that runtime:

| Runtime built with | Result |
|---|---|
| `-O2` (the default), `-O0`, `-O1`, `-O3`, `-Os` or `-Oz` | Passes |
| LLVM's basic or PBQP register allocator (`-mllvm -regalloc=`) | Passes |
| `-fprofile-instr-generate`, with or without `-fcoverage-mapping` | Fails in both tiers |

So the instrumented runtime of `make runtime-coverage` is the variant that found it, and the
Coverage workflow's runtime jobs run the corpus with it daily. Its counters stay plain: atomic
ones (`-mllvm -instrprof-atomic-counter-update-all`) hid the bug as well. The runtime built at
`-O1` passed the JIT corpus (3,367 checks on `9390e78f`) and is left out of the variants: it does
not expose the retention either, and unlike `-O0` it still optimizes an AOT program's module.

### Job times

CI's groups target under ten minutes of work, within a 15-minute limit
([#562](https://github.com/den-run-ai/pystachy/pull/562)). The Coverage workflow ran as one
38-minute job when [#731](https://github.com/den-run-ai/pystachy/pull/731) added it, and this
review's first split still ran jobs of 9 to 15 minutes on `655db8ac`
([run 39365631098](https://github.com/den-run-ai/pystachy/actions/runs/39365631098)): the
corpus's thirds took 13.6, 15.0 and 9.3 minutes, and the runtime's job 12.9. The same third took
9 to 14 minutes on different runners. The hosted corpus now runs in eighths, the runtime's in
sixths and each variant in quarters, each in a job of its own, and Lint's
`tools/test_workflow_limits.py` fails a workflow job that has no limit or one over 15 minutes
([continuous integration](../testing.md#continuous-integration)).

## Next steps

1. Keep the coverage runs and the variants scheduled and advisory; review the changed code that a
   pull request's run lists, and require a failing regression test for each fix instead of a
   percentage.
2. Add tests for the code-generation sites still listed as missed, starting with those reachable
   from ordinary programs; then rejection fixtures for the diagnostics that users meet.
3. Support `iter()` of a `bytes`, and `sys.exit()` of a tuple of run-time length.
4. Remove the runtime functions that no compiled program calls, or give them callers, and leave
   the scalar branch out of the merges' copy for sorts that keep an undo record, which no sort of
   scalars reaches.
5. Measure what the blind spots hide: continuous-mode profiles for signal deaths, and
   `runtime.py`, which no instrumentation reaches.
