===== repo-abi 28785
Pystachy's ABI is easy to call from C, but its runtime assumes it owns the whole process. Compiled functions are `define internal` with the default C calling convention (ccc, never fastcc). Their symbols are not valid C identifiers (@f.name, @f.mod$name, @m.Class.meth, @f.name.N, @init.mod, @main.init). LLVM types: int is i64, float is double, bool is i1, a None return is void, and everything else is a ptr (str, list, dict, tuple, object, optionals, boxed int|None). The only attribute is `nonnull` on self, plus the pys_personality routine when the function has landing pads.

The GC is conservative and non-moving. It ignores any word outside its own page map, so a PyObject* stored in a slot does no harm, but nothing traces it, retains it or finalizes it. Its roots are only the stack between the collector and @main's frame (gc_bottom), the table of pointer-typed globals and runtime statics. I verified three failures with experiments under PYSTACHY_GC_STRESS=1:
- **Init from a deeper frame:** calling Pystachy code after initializing from a deeper frame crashes with SIGSEGV. A CPython extension always hits this, because PyInit runs under importlib's deep C frames.
- **Foreign-held objects:** Pystachy objects held only in malloc memory or a PyCapsule are collected and their memory reused, so reads silently return wrong data.
- **Exceptions in callbacks:** a Pystachy exception raised inside a C callback silently skips the C frames when they have unwind tables, and exits the process when they do not.

The runtime also calls exit()/_exit(), hijacks SIGINT (verified: CPython never sees KeyboardInterrupt), resets LC_CTYPE, keeps its own stdout buffer, and has no locks.

A 12-line prototype in a scratch copy of runtime.c makes a real CPython 3.13 extension pass under GC stress. It adds pys_lib_init (no signals, exceptions on), pys_enter/pys_leave (the outermost entry frame bounds the stack scan), pys_pin/pys_unpin (extra roots), and wrappers that catch every exception and turn it into an error. The repo itself was not touched.

The extern mechanism of runtime mode (`def f(...) -> T: ...`, limited to int, float, str and None, called with every effect letter (FXALL)) can be generalized for Pystachy calling C. It needs an explicit opt-in marker, because today that form compiles to a RuntimeError. The JIT already works with lli --dlopen and -extra-object (verified by calling libpython). For AOT, PYSTACHY_CFLAGS=-l... already reaches the link.
-- implications
 * Recommended split: use AOT for C calling Pystachy, which includes a CPython extension (bidirectional when the shim calls the C API). Use both tiers for Pystachy calling C: the JIT through `lli --dlopen`/`-extra-object` at pystachy.py:16670, AOT through llvm-link or the link line at 16646/16653. Do not host the JIT inside CPython: today the JIT is lli exec'd as a separate process (16670-16671), so that would need in-process ORC, the largest change.
 * Pystachy calling C, ranked by blast radius:
- **(1) Driver only, about 3 lines:** pass --dlopen/-extra-object/-extra-module to lli at 16670 and -l/objects/.bc to the AOT link at 16646/16653. PYSTACHY_CFLAGS=-lfoo already works for AOT. No invariant is at risk.
- **(2) Compiler-internal bindings:** add RUNTIME raw-symbol and CALLS entries (as fabs is). That is 2 lines per function, but not user-facing.
- **(3) User extern declarations, about 20-40 lines:** generalize runtime mode's `def f(...) -> T: ...` at pystachy.py:8015-8021 and 10925-10945, with an explicit opt-in marker, the untold() type set (int, float, str, None; bool rejected or widened to i64), and FXALL effects for free. The risk is the CPython-equivalence contract: CPython returns None for `...`, so a ctypes-based fallback module is needed, as with tools/rt_cpython/_rt.py.
- **(4) Opaque owned handles (PyObject*), about 30 lines:** generalize files_sweep (runtime.c:1815) into a handle-finalizer queue drained after collect() returns, never during it: Py_DECREF can run Python code that re-enters Pystachy.
 * C calling Pystachy, ranked by blast radius:
- **(1) Pystachy main with C callbacks, about 10-20 lines:** the GC is already sound here. It needs external linkage and C names for chosen functions (9778 forces `internal`; names contain '.' and '$') and a catch-all at each callback boundary.
- **(2) Library mode, about 12 lines in runtime.c plus 40-80 in the compiler and about 10 in the driver:** add pys_lib_init, pys_enter/pys_leave and pys_pin/pys_unpin (prototype verified under GC stress). Emit export wrappers (frameaddress, enter/leave, try_mark, invoke, catch-all landing pad, exc_begin, exc_restore, error out-parameter; bool as i64) instead of @main at 11068-11084. Add -fPIC, -shared and visibility flags at 16653.
 * Invariants an FFI must protect:
- **Stack bottom:** set gc_bottom at the outermost foreign entry, or use the thread's stack base.
- **Foreign-held references:** pin every Pystachy object that foreign memory holds.
- **Exception boundary:** never let a Pystachy exception cross a foreign frame, and turn exceptions on in library mode (Gen.eh is closed-world today).
- **No exit() in a host:** library mode must not install the SIGINT handler, call setvbuf or reset the locale, and must flush stdout at the boundary or route print to PySys_WriteStdout. oom() still calls exit(1).
 * Threads: the runtime has one global heap and no locks. Calls must come from one thread, and the GIL must not be released while Pystachy frames are live on another thread. Under free-threaded CPython the extension should declare Py_mod_gil = Py_MOD_GIL_USED (CPython API name unverified here).
 * Keep the extern type set scalar plus str (plus an int-typed opaque handle). This matches runtime mode's untold rule, which rtabi.py can check, and maps directly to Wasm imports for the planned Wasm GC backend. FFI declarations must stay out of runtime.py, which must hold no raw pointers.
 * A str at the boundary is Str* (len at offset 0, bytes at +8, NUL-terminated), so C can read s+8 as a const char* without copying. CPython str and bytes must be copied through pys_str. Pystachy str is UTF-8 bytes and int is a checked 64-bit value, so the boundary must check: PyLong out of range raises OverflowError, and lone surrogates need a policy.
 * Generated wrappers and a pystachy.h could reuse the descriptor language (desc(), pystachy.py:7559) to marshal lists, dicts and tuples generically, as pys_repr walks values in C. check_runtime.py's call-graph effect inference could derive effect letters for user C helpers instead of FXALL.
===== repo-docs 26928
The repo docs leave CPython interop undecided. history.md:73 lists "Standalone mode, or also a CPython-extension mode (open, nothing decided)". Issue #4 §4 calls the AOT extension mode "a recommendation to evaluate, not an already approved implementation decision" and says "Preserve standalone mode". The only concrete design is typed-ir.md §7.4 (lines 1122-1132): a third lowering of eligible IFns in which containers stay Python objects, None is Py_None, refcounts are derived in that lowering only, check/raise become PyErr_* plus an error return, and the boundary checks or rejects 64-bit int and byte-indexed str.

Hard invariants:
- the CPython-or-compile-error contract;
- the three-stage byte-identical fixed point, which also covers runtime.py's IR;
- the Python-free stage;
- irsame (byte-identical IR for refactors), with the pay-for-use precedent that a feature leaves programs that don't use it byte-identical;
- the UBSan, gc-stress, check-ir, runtime-table and rt-abi steps.

Soft preferences: a runtime that needs only libc, no second toolchain (Rust, Zig and C++ were rejected for that reason), runtime.py that CPython can still run (inline LLVM IR was rejected for that reason), and a raw-pointer-free _rt for Wasm GC.

Today's only extern mechanism is runtime-mode `def pys_x(...) -> T: ...`, limited to runtime.c's pys_* symbols. It has no bool in signatures, its untold signatures are limited to int/float/str/None, and rtabi and check_runtime verify it. Programs cannot declare externs.

Runtime facts that block bidirectional use:
- GC roots run from the collector's frame up to @main's frame, plus a registered globals table, so the foreign heap is never scanned.
- pys_init installs SIGINT/SIGPIPE handlers and stdout buffering.
- Errors call exit().
- Forced unwinding passes over frames that have no pys_personality, so it would skip CPython's frames without cleanup.
- State is single-threaded and closed-world.
- `__del__` never runs, but the sweep already closes unreachable files, which is a precedent for releasing foreign handles.
- The JIT is a separate `lli` process reached by exec.

The typed IR cannot host a third lowering yet: about 58k raw ops still hold LLVM text, and step 16 has not started. It also needs recoverable elaboration. Its premise "the subset has no exceptions" has been stale since #22, although the compiler itself still uses no try.

Two probes:
1. LLVM 18's `lli --dlopen=libpython3.13.so` ran embedded CPython 3.13.16 in-process, so embedding works under the JIT tier.
2. clang alone (no Python.h) built an extension module from hand-written LLVM IR, using only abi3-style symbols. CPython imported it, and checked-int overflow mapped onto OverflowError and TypeError.

Net: the docs point to an AOT extension lowering and keep the standalone tier unchanged. Nothing in them covers an in-process JIT, and that would need a new toolchain.
-- implications
 * Design every FFI feature as pay-for-use: programs that don't use it must keep byte-identical IR. That keeps irsame, the three-stage fixed point (runtime.py included) and the existing corpus untouched, as #22's exceptions and #19's runtime.py did.
 * Keep the CPython oracle. Any FFI declaration a program uses must also run under CPython. Follow the _rt precedent: a module Pystachy lowers to direct calls, plus a CPython twin (e.g. ctypes-backed) that tools like rtcheck can test against. A bare `def f(...) -> T: ...` in user code would run as returning None under CPython, which breaks the contract.
 * Reuse the existing binding tables instead of a new mechanism. RUNTIME ('result:params|effects|symbol') and CALLS already describe foreign C symbols, and rtabi and check_runtime already verify them. Give user externs conservative effects (all letters but N) and the same rules: no bool in signatures, and only int, float, str or None where nothing else can check the signature.
 * Never let raw pointers into runtime.py or _rt, so it still lowers to Wasm GC. Confine externs and PyObject handles to program code or a separate shim, with only int/float (and str by copy) as portable boundary types.
 * For CPython → Pystachy (AOT extension), the documented direction is a third typed-IR lowering (typed-ir §7.4): Py_None, refcounts from liveness, PyErr_* plus error returns via the error flag, and int and str boundary checks. It is blocked on typed-IR step 16 and on recoverable elaboration. Since #22, recoverable elaboration could use the subset's own try/raise inside the compiler. Note that this changes the compiler's own IR: it is a re-baselining step, not a byte-identical one.
 * A lower-impact first step for AOT extension output is possible with today's toolchain: the probe shows clang alone can emit an abi3-symbol extension .so from LLVM IR, with no Python.h and no Python at build time. So the compiler build stays Python-free, and only the tests of the mode need python3 (a separate verify step).
 * A wrapper-style extension that links runtime.c into the .so needs:
- a GC root window set at each entry;
- a root table for Pystachy objects referenced from CPython;
- a catch-all landing pad at every exported entry, converting to PyErr, because forced unwinding would otherwise skip CPython frames;
- no exit() on errors;
- no pys_init signal or stdout takeover inside a host interpreter.
 * Bidirectional calls (Pystachy → CPython → Pystachy) need four things the docs don't have yet:
- functions as values (M3) for callbacks;
- a refcount release hook at sweep, modeled on how files are closed at collection, since __del__ never runs;
- a policy for cross-runtime cycles;
- a mapping of arbitrary Python exceptions into the closed exception-class world.
 * On JIT vs AOT, the docs only ever say AOT for CPython interop (issue #4 §4, typed-ir §7.4). The JIT tier can still reach C externs (-extra-object/--dlopen) and even an embedded libpython (lli --dlopen, verified), at no toolchain cost. An in-process JIT inside CPython would need an LLVM binding in the host, a new dependency against the documented no-new-toolchain rationale. A decorator front end is best done as an AOT compile with a cached .so.
 * Effects: every foreign or PyObject op is U, R, A and I, so the listget and dictfuse optimizations stop at it and calls inside a try become invokes. FFI-heavy regions lose the typed-IR optimizations unless effect annotations are trusted and checked.
===== web-capi 24660
As of 2026-10-09, CPython 3.15.0 is out: PEP 790 lists 3.15.0 final for 2026-10-09 and the v3.15.0 tag exists. It brings the first stable ABI that free-threaded builds can load. PEP 803 adds "abi3t": PyObject is opaque, and Py_INCREF, Py_DECREF, Py_TYPE, Py_SIZE, Py_IS_TYPE and Py_None all become calls to exported functions. A module built with Py_TARGET_ABI3T=0x030F0000 is named `.abi3t.so` and loads on both GIL and free-threaded 3.15+. abi3t requires the PEP 793 entry point (`PyModExport_<name>` returning a PEP 820 `PySlot` array) and a mandatory `Py_mod_abi` slot. Other C API changes:
- Limited 3.14: PyLong_AsInt64 and PyLong_FromInt64.
- Limited 3.15: PEP 757 export, PyCriticalSection, and the PEP 788 thread-attach calls.
- Not in the Limited API: PyBytesWriter, PyUnicodeWriter, PyTuple_FromArray and PEP 741 PyInitConfig.

Two efforts have stalled. PEP 809 (abi2026 with an interfaces table) is still a Draft with no decision. HPy declared itself unmaintained in September 2026 and points to the draft PyNI PEP: handles, a context argument and a function table.

For a compiler that emits LLVM IR: every operation needed is an exported Stable-ABI function. The Stable ABI docs say they are usable "in languages that don't use the C preprocessor". The 3.15 abi3t headers themselves compile Py_INCREF to `call @_Py_IncRef`, Py_None to `call @Py_GetConstantBorrowed(0)`, and PyLong_Check to `Py_TYPE`+`PyType_GetFlags`. So generated IR should call the C API directly; no clang shim is needed for abi3/abi3t.

I checked this end to end:
- A pure-IR module with no headers, no shim and no libpython link, built with `clang -shared`, imports and works on both CPython 3.15.0b4 and 3.15.0b4t. It covers checked-int add, OverflowError, and calling back into Python through vectorcall with Python exceptions passing through.
- `Py_mod_gil` USED re-enables the GIL on 3.15t with a RuntimeWarning.
- Leaving out `Py_mod_abi` is a SystemError.
- Embedding works from the JIT tier with `lli -dlopen=libpython3.X.so`, tested on 3.13 and 3.15t.

A C shim only pays off for a version-specific (non-stable) build that wants inlined refcount fast paths, or for Windows. Recommendation from the C API side: an AOT `.abi3t.so` for CPython→Pystachy. For Pystachy→CPython, both tiers can call libpython.
-- implications
 * Use AOT for CPython->Pystachy, i.e. extension modules. CPython only imports shared objects, and `pystachy run` execs lli as a separate process (pystachy.py:16670), so the JIT cannot host an extension. Minimal change: reuse the existing llvm-link of program plus runtime bitcode (pystachy.py:16646-16653), then run `clang -shared -fPIC` to produce `<mod>.abi3t.so` instead of an executable. Do not link libpython.
 * Target abi3t 3.15 (abi_version 0x030F0000, flags STABLE|GIL|FREETHREADED). One binary then covers GIL and free-threaded CPython 3.15+, wheel tag cp315-abi3.abi3t. Optionally add abi3 for 3.12-3.14 later, through PyInit_ and PyModuleDef with the version-specific header, which needs a C shim or careful IR.
 * Generated IR should call the Stable ABI directly, with no C shim. Every macro or static inline has an exported equivalent, and the abi3t headers compile to exactly those calls:
- Py_INCREF/DECREF -> Py_IncRef/Py_DecRef (NULL-tolerant) or _Py_IncRef/_Py_DecRef (abi_only).
- None/True/False -> Py_GetConstantBorrowed(0/2/1).
- Exact type test -> Py_IS_TYPE(o,@PyLong_Type), or icmp on Py_TYPE(o).
- Subclass test -> PyType_GetFlags(Py_TYPE(o)) & (1<<24 long, 25 list, 26 tuple, 27 bytes, 28 str, 29 dict).
- Critical section -> alloca 16B plus PyCriticalSection_Begin/End.
This needs no Python headers and no Python on PATH at build time, which fits the CI rule.
 * Keep a checked-in declarations table, comparable to RUNTIME, generated from Misc/stable_abi.toml. Add a CI check that `nm -D --undefined-only` of the .so is a subset of the Stable ABI for the target version.
 * Emit module data in IR: PySlot {i16,i16,i32,ptr}, PyABIInfo {i8,i8,i16,i32,i32} and PyMethodDef {ptr,ptr,i32,ptr}, with the 3.15 slot IDs (Py_mod_abi 109, Py_mod_name 100, Py_mod_methods 103 with the STATIC flag, Py_mod_gil 87, Py_mod_multiple_interpreters 86).
 * Declare Py_mod_gil=Py_MOD_GIL_USED and Py_mod_multiple_interpreters=NOT_SUPPORTED. The runtime's GC and heap are process-global and single-threaded (runtime.c:56,162). On 3.15t the GIL is then re-enabled with a RuntimeWarning, which is correct and the least invasive choice. GIL-free support would need a thread-safe runtime.
 * GC roots: today @main passes its frame to pys_init as the stack bottom (runtime.c:56,1839,162). In extension mode there is no @main. Every exported entry trampoline must record the stack bottom at the outermost Python->Pystachy entry, and pys_init must run lazily, for example from Py_mod_exec. Re-entrant callbacks (Py->Pys->Py->Pys) need a nesting counter.
 * Exceptions must not unwind through CPython frames. Each exported function needs a landing pad under pys_personality (runtime.c:2369; forced unwind at runtime.c:2319) that converts a Pystachy exception to PyErr_SetString(PyExc_*) and returns NULL. A NULL from any C API call becomes PyErr_GetRaisedException (3.12) and is re-raised as a Pystachy exception. PyO3 handles panics the same way.
 * Boundary conversions, which follow typed-ir.md §7.4's 'boundary checks':
- int: PyLong_AsInt64/PyLong_FromInt64 (Limited 3.14), which raises the same OverflowError as Pystachy's checked int.
- str in: PyUnicode_AsUTF8AndSize (cached UTF-8; fails on surrogates; byte length differs from CPython len, so reject or convert).
- str out: PyUnicode_DecodeUTF8 or PyUnicode_FromStringAndSize.
- bytes: PyBytes_FromStringAndSize (PyBytesWriter is not limited).
- Containers: PyList_New/SetItem, PyTuple_New/SetItem, PyDict_New/SetItem, plus PyList_GetItemRef and PyDict_GetItemRef rather than borrowed getters.
- Calls: PyObject_Vectorcall with PY_VECTORCALL_ARGUMENTS_OFFSET. Avoid variadic Py_BuildValue and PyArg_ParseTuple.
 * Object lifetimes in both directions: PyObject* stored in the Pystachy heap is never Py_DecRef'd, because __del__ never runs. Either forbid storing PyObject* in Pystachy objects, copying at the boundary, or add a sweep hook for PyObject boxes. To pass Pystachy objects to Python, use PyCapsule (Stable ABI since 3.2) plus a GC root table, with a capsule destructor that unregisters the root. This avoids defining heap types (PyType_FromSlots) in the first iteration.
 * Keep all CPython glue out of runtime.py, because the WasmGC backend forbids raw pointers there. Put it in the compiler's third lowering (typed-ir.md:1122-1132), or in a C file linked only in extension mode.
 * Pystachy->CPython (embedding) works in both tiers: JIT via `lli -dlopen=libpython3.X.so`, verified on 3.13 and 3.15t, and AOT via -lpython3.X. Only Py_InitializeEx/Py_FinalizeEx are stable; PyInitConfig is not. Treat embedding as version-specific and secondary.
 * Portability of direct IR: C `int` is i32 and Py_ssize_t is i64 on 64-bit. PyType_GetFlags returns `unsigned long`, which is i64 on Linux and macOS but i32 on Windows. Windows also needs python3.dll and __imp_ data imports. Signext/zeroext attributes are target-dependent. Direct IR is fine for Linux x86-64; other targets need per-target declarations or a clang-compiled shim.
===== web-peers 28031
I surveyed 18 peers from primary sources: docs, changelogs and source code at their Oct 2026 HEADs. They share one pattern.

**Calling C.** The most portable approach is a hand-written typed stub per function. Examples are Codon `from C import f(int)->float`, Julia `@ccall`, LPython `@ccall`, and Shed Skin's ".py type model". Header importers all carry a libclang- or Aro-sized dependency: Zig translate-c (moved out of the language into the build system; @cImport deprecated in 0.16 and reported removed in 0.17), Swift ClangImporter, and Rust bindgen.

**Calling CPython.** Compilers that emit LLVM or C call exported stable-ABI functions such as `Py_IncRef`. They load libpython with dlopen at run time (`CODON_PYTHON`, `MOJO_PYTHON_LIBRARY`, pythonnet `Runtime.PythonDLL`), so it works under both their JIT and their AOT build.

**Being called from CPython.** This is almost always an AOT extension module: `codon -pyext`, Mojo `PythonModuleBuilder`, mypyc, Cython, Shed Skin `-e`, SPy `py-cffi`. "JIT" decorators are mostly a compile on first call into a cached .so (LPython `@lpython`, `mojo.importer`). A real in-process JIT (`codon.jit`, Numba) requires the compiler to run as a library inside CPython.

**Lifetimes across two memory managers** use two mirror-image mechanisms:
- **Native objects held by Python:** a handle table rooted in the native GC, freed in `tp_dealloc` (PythonCall `PYJLVALUES`, Shed Skin `__ss_proxy`, pythonnet GCHandle, Go `cgo.Handle`).
- **Python objects held by native code:** releases are deferred and run only while the thread is attached to the interpreter (holds the GIL). Examples: PyO3's reference pool, pythonnet's `Finalizer` queue, the PythonCall GC queue, Codon `pyobj.__del__`.

**Exceptions** never unwind across the boundary. They are caught at every trampoline and turned into `PyErr` plus NULL (PyO3 `catch_unwind` → `PanicException`, Shed Skin `catch(Exception*)`). Rust and Swift abort, or the behaviour is undefined, when an unwind crosses a C frame.

**Closest peers.** Codon is architecturally closest to Pystachy: LLVM output, JIT plus AOT, its own conservative GC (Boehm), C FFI and Python interop in both directions, Py* functions resolved with dlsym. Shed Skin is closest in language and runtime: an implicitly static subset, Boehm GC, 64-bit int, and an extension-module mode with a proxy-dict lifetime bridge. LPython is closest on the "same file must run under CPython" contract: its `@ccall` falls back to ctypes under CPython.

**Verified locally:** LLVM 18 `lli --dlopen=libpython3.12.so.1` runs IR that embeds CPython. Pystachy's JIT tier could therefore call into CPython with one extra flag.
-- implications
 * Twelve practices carry over from the peers. The first ten are below; the last two items in this list cover handle checks and JIT versus AOT.
 * 1. Make the foreign declaration valid Python that CPython can run. Generalize the existing runtime-mode stub (pystachy.py:8015-8020) to user code, for example a decorated `def f(x: int) -> float: ...` that names a library. Ship a small pure-Python shim that binds the same stub through ctypes when the file runs under CPython. This is LPython's @ccall pattern (lpython.py:337-486). It keeps the 'prints what CPython prints' oracle and the self-hosting fixed point, because the compiler itself never needs the shim.
 * 2. Keep the C ABI narrow at first. Allow int (i64), float (double), bytes/str as a pointer plus length, a pointer-sized opaque handle, and bool passed as int (already enforced at pystachy.py:10931). Do not pass or return structs by value; Codon and Numba both warn against or forbid it. Leave header import (Zig translate-c, Swift ClangImporter, bindgen) to optional offline tooling, never the compiler. Zig itself has moved translate-c out of the language.
 * 3. Never let a Pystachy exception unwind across a foreign frame. _Unwind_ForcedUnwind (runtime.c:2319) would run through CPython or C frames that have no cleanup code. Every exported entry and every C callback needs a catching trampoline that converts the exception to PyErr_* plus a NULL/-1 return, as PyO3, Shed Skin and Codon -pyext do. In the other direction, check every C-API result for NULL/-1 and re-raise it with PyErr_GetRaisedException, not the deprecated PyErr_Fetch that Codon still uses. Wrap the original exception object (pythonnet 3.0) rather than flattening it to a message.
 * 4. Encode reference ownership (new, borrowed, stolen) in the RUNTIME signature table. This is the 'new-or-borrowed column' of docs/typed-ir.md §7.4, the same idea as pythonnet NewReference/BorrowedReference/StolenReference, PyO3 Bound/Borrowed/Py, and Mojo from_owned/from_borrowed/steal_data. Derive the incref/decref calls from liveness in the lowering.
 * 5. Python objects held by Pystachy code need explicit release, because __del__ never runs and the GC has no finalizers. One option is scoped lifetimes: decref at last use or at the end of a with-block. The other is a new 'foreign handle' object kind whose sweep only queues a Py_DecRef, which is then drained while attached to the interpreter. That is the PyO3 reference pool, pythonnet Finalizer and PythonCall GC.enqueue pattern. Codon instead relies on Boehm finalizers, which Pystachy's GC lacks.
 * 6. Pystachy objects held by Python must be registered in a root table and removed in tp_dealloc. Python's heap is invisible to the conservative scanner, so these objects would otherwise be freed while still in use. This is the PythonCall PYJLVALUES, Shed Skin __ss_proxy, pythonnet GCHandle and Go cgo.Handle pattern. runtime.c:163 already scans a gc_roots table; it needs to become growable with a free list. The GC does not move objects, so pinning costs nothing.
 * 7. In extension or callback mode, set the conservative stack bound at the outermost entry, or to the thread's stack base, not at @main's frame (runtime.c:104, 1839). The collector is single-threaded, so mark extension modules Py_mod_gil = Py_MOD_GIL_USED. Never release the GIL while Pystachy code runs, and reject calls from other threads.
 * 8. Copy built-in containers at the boundary and proxy only opaque objects (Shed Skin, the Codon JIT, Pyodide, pythonnet 3.0's explicit codecs). Make every conversion checked: PyLong_AsLongLong gives OverflowError, matching Pystachy's checked int. Python str to UTF-8 is cheap, but Pystachy's len counts bytes, so non-ASCII text must be rejected or flagged at the boundary (typed-ir §7.4). Codon dropped its UTF-8-bytes str in 0.20 for this compatibility reason.
 * 9. Call only exported stable-ABI functions, resolved by symbol, never C macros or struct layouts; Codon does this with dlsym. An LLVM-emitting compiler cannot use Python.h macros anyway. For extension output targeting 3.15+, emit PEP 793 PyModExport_<name> returning a constant slot array, and aim for abi3t (PEP 803) so one .so serves both GIL and free-threaded builds. Expect a Limited-API cost of roughly 5-20% on object-heavy code (Cython's measurement).
 * 10. Load libpython lazily so standalone binaries stay free of it (SPy's plan; Codon CODON_PYTHON; pythonnet PythonDLL). JIT: add `--dlopen=<libpython or C lib>` to the lli command line at pystachy.py:16670 (verified working with lli-18). AOT: dlopen at first use, or link with -l. Extension mode resolves Py* from the host process (Codon's dlopen("")).
 * 11. Add a debug check that counts live handles and pending decrefs at exit (nanobind's leak report, cgocheck, pyo3_disable_reference_pool). Run it in `make verify`.
 * 12. JIT versus AOT, from the peers: Pystachy calling CPython (embedding) works in both tiers today, the JIT via --dlopen and AOT via dlopen. CPython calling Pystachy should be AOT only: an extension module, optionally compiled on import and cached as LPython @lpython and mojo.importer do. ===== web-gc 26381
Recommendation from the GC side: build AOT first, as a CPython extension .so made by `pystachy build`. The runtime.c machinery below can later serve a JIT-hosted embedding (lli --dlopen libpython). It cannot serve Python→Pystachy in-process, because `pystachy run` execs a separate lli process.

The systems surveyed each have their own GC beside CPython's refcounts: PyPy rawrefcount/HPy, GraalPy, pythonnet, JPype, PythonCall/juliacall, Pyodide (PEP 818), Codon, Mojo, and Boehm GC users. They converge on four pieces, which map onto Pystachy as follows.

(a) Pystachy→Python references get an ownership class from the compiler:
- **Borrowed:** call arguments, with no refcount operations (HPy-handle-like).
- **Owned local:** Py_DECREF at last use, and released on a raise through the existing unwind-action list.
- **Escaped:** incref plus a GC-tracked atomic box. A post-mark sweep cloned from files_sweep queues the dead boxes' PyObject*s, and a safe point drains the queue with the thread attached (PyPy, pythonnet and PythonCall all defer the decref this way). close() gives prompt release.

(b) Python→Pystachy uses a root-scanned pin table. Each heap-type wrapper (tp_dealloc unpins) or PyCapsule (its destructor unpins) gets one slot. An address→wrapper side map keeps identity, since the GC is non-moving.

(c) Cross-heap cycles are documented as leaks, as PEP 818, JPype and nanobind-on-PyPy all do. Offer weak refs and close(), and count pins and boxes in PYSTACHY_GC=stats. Cross-component tracing (GraalPy, V8/Blink) is deferred.

(d)/(e) The single @main gc_bottom is replaced by per-thread records {bottom of the outermost entry, park top, depth}. Every C-API call that can run Python code "parks": it spills the callee-saved registers, then records sp in a noinline helper (the Boehm GC_do_blocking pattern). The collector scans its own [frame, bottom] plus each parked thread's [top, bottom].

Two experiments confirmed the design:
- Without spill-then-record, a pointer kept in a callee-saved register across a callout was missed 200/200 times; with it, it was found 200/200.
- _Unwind_ForcedUnwind walks straight through CPython frames to _start, so every boundary must catch Pystachy exceptions and convert them to and from PyErr.

On GIL builds the GIL serializes Pystachy code; the exception state becomes per-thread. On free-threaded builds, v1 leaves Py_mod_gil unset and refuses import if PYTHON_GIL=0 kept the GIL off. v2 adds a PyMutex world lock released at park, then declares Py_MOD_GIL_NOT_USED. There is one world per process, declared with Py_MOD_MULTIPLE_INTERPRETERS_NOT_SUPPORTED.

Estimated runtime.c changes: about 150-200 lines for the GC core, about 230-300 with extension-mode init and the free-threading lock.

- Make xr and unw per-thread in extension mode (about 20 lines).

 * Total runtime.c estimate: GC and lifetime core about 150-200 lines; about 230-300 with extension-mode init (no argv, signals or stdout setup, no exit) and the free-threading lock.  * In-process JIT inside CPython is feasible with no new dependency (ctypes plus the system libLLVM 18), at about 28.5 ms against about 42 ms for an lli subprocess. It needs libgcc_s preloaded with RTLD_GLOBAL and the runtime added as a precompiled object, not bitcode (735 ms). It is fragile: it pins the system libLLVM's exact version and needs ctypes prototypes for each C API function. AOT extension modules are much cheaper per call (about 47 ns against about 270 ns through ctypes) and start in 0.4 ms. The evidence therefore favours AOT for Python-to-Pystachy, with JIT as an option for embedding (Pystachy-to-Python) and for development.
