[27] (medium) (a) User-declared C externs: interaction with each invariant.
- Contract: broken unless CPython can run the same declaration. A `...` body returns None under CPython, so a CPython twin (ctypes-backed, like _rt's twin) is needed.
- Fixed point and irsame: unaffected if programs that use no extern keep their IR (pay-for-use).
- Python-free: fine.
- Runtime: no growth if calls are direct; the effects are conservative (all but N).
- UBSan and gc-stress: pointers held by C beyond the call would be invisible to the GC.
- Wasm GC: portable only for int/float (str by copy) as host imports, and externs must stay out of runtime.py to keep _rt pointer-free.
- Tiers: both reach C symbols, AOT through the link and the JIT through -extra-object/--dlopen.
   EVID: Inference from pystachy.py:8015-8020, docs/runtime-in-subset.md:68,119,123,143-145, docs/typed-ir.md:476, runtime.c:161-170, lli --help (--dlopen/--extra-object)
[28] (medium) (b) CPython extension-module output (AOT): interaction with each invariant.
- Status: the only option the docs sketch (typed-ir §7.4, issue #4 §4).
- Contract: testable by importing the compiled module and its source into CPython and comparing. The deviations (64-bit int, byte str) must be checked or rejected at the boundary.
- Fixed point and irsame: unaffected if the lowering is a separate output mode.
- Python-free: compiler builds stay Python-free (the probe shows no headers are needed), but tests of the mode need python3, so they belong in a separate verify step.
- Prerequisites: the full typed-IR lowering needs step 16 and recoverable elaboration first.
- Runtime: it does not use runtime.c, but needs C-API helpers (mypyc's lib-rt is 29k lines of C over the C API).
- Wasm: no conflict.
- Lighter variant (my inference, not in the docs): wrap the existing LLVM lowering plus runtime.c into a .so with copy-converting entry wrappers, a gc_bottom per entry and handles kept as roots. That needs no third lowering but contradicts "keep mutable Python objects as Python objects" unless the copies are explicit.
   EVID: docs/typed-ir.md:1122-1132, 25-27, 1180; docs/runtime-in-subset.md:426, 630; GitHub issue #4 §4; probe pysq.ll
[29] (medium) (c) Embedding CPython in Pystachy programs with an opaque PyObject type: interaction with each invariant.
- Status: named in #4 §4 as "explicit opaque-Python-object bridging", to compare in the ADR; Codon is cited, where converted containers do not preserve shared mutation.
- Contract: holds only if every PyObject op has CPython semantics, and the oracle is CPython running the program natively.
- Runtime: needs an opaque type (M4's Any is not started), U+R+A+I effects on every op, PyObject* refcounts released by a sweep-time hook (as files are; __del__ never runs) and a policy for cross-runtime cycles.
- Runtime dependency: needs libpython at run time, which breaks the libc-only runtime unless it is optional or dlopen'd. Both tiers can load it (JIT through lli --dlopen, verified).
- Exceptions: Python exceptions fall outside the closed class set and need a catch-all mapping.
- Stdout: Python's sys.stdout and Pystachy's C stdout buffer interleave.
- Callbacks: Python calling into Pystachy needs functions as values (M3, not supported).
- Wasm GC: not portable.
   EVID: GitHub issue #4 §4; docs/typed-ir.md:1147-1148, 1456-1457; docs/language.md:578-579; docs/internals.md:247; README.md:52,247; runtime.c:1851; probe emb.ll
[30] (medium) (d) In-process JIT inside CPython (a Numba/LPython-style decorator): no doc mentions it.
- Tooling: Pystachy's JIT is an exec'd lli process, and the compiler drives LLVM only through command-line tools. An in-process JIT needs an LLVM binding inside CPython, which is a new toolchain dependency (contrary to the no-new-toolchain rationale). The other route is an AOT compile to a cached .so loaded behind the decorator, which is (b) with a cache.
- Contract: a natural fit, since the undecorated function runs on CPython as the oracle.
- Templates: specialization per argument types matches templates, but instance names are not stable for export.
- Runtime: pys_init's signal and stdout setup and exit()-on-error would act on the host process.
- Compile cost: the CPython-hosted compiler is about 6x slower than the native one (2.6 s against 0.45 s for 16k lines).
- Python-free: an inherently Python-hosted mode, outside that stage.
