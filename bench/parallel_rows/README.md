# Ordered row scoring on verified numeric workers

This prototype extends [#1088](https://github.com/den-run-ai/pystachy/pull/1088)
(`163fe22c9bfcdb6c299bf65998cf003d151b6132`) with one allocating owner operation,
`parallel.sum_rows_float(callback, flat_values, width, workers=1)`. It applies a
known, proven scalar callback to every element and returns one float per row.
Each row starts at `+0.0` and accumulates from left to right. Workers process
whole rows, so there is no reassociation or partial reduction across threads.

The compiler resolves an immutable known callable, then applies #1088's existing
strict proof to its final optimized scalar body. Accepted bodies contain bounded
acyclic scalar arithmetic, comparisons, branches and private locals. Helper
calls, user loops, globals, allocations, exception machinery and runtime calls
remain ineligible. An empty effect summary alone does not qualify a callback.
Unknown/effectful callbacks use the shipped Python implementation, preserving
ordered side effects, live element reads and the first raised exception.

The row loop is generated by the compiler. Its bounds come from the owner's
checks that `width > 0` and `len(values) % width == 0`; `row * width + column`
is consequently within the input length. The runtime allocates a fresh result
before dispatch. Workers receive raw input/output arrays and an immutable width;
they never touch managed metadata, the allocator, exception state or GC. The
owner retains both allocations and waits for all started workers before returning
or delivering a deferred SIGINT. Partial launch failure computes only unlaunched
chunks on the owner. The existing map dispatcher is shared; its generated thunk
has an additional internal width argument, but the public `map_float` API and
scalar eligibility contract are unchanged.

The worker count defaults to one. At least 16,384 input elements are required per
participant, and participants are capped by the number of rows. This is a bounded
heuristic, not a measured optimal policy. A single long row always stays serial.
See [the concurrency contract](../../docs/concurrency.md) for the precise API and
its connection to the other parallelism experiments.

## Reproduce

From the repository root, with LLVM 18 and the pinned CPython available:

```sh
python3 bench/parallel_rows/run.py --compiler ./pystachy \
  --cpython /path/to/pinned/python3.13 --output /tmp/parallel-rows.json
```

`--compiler` and `--cpython` accept shell-quoted command strings. For a development
compiler, use `--compiler 'python3 pystachy.py'`. `--smoke` validates the complete
harness with 17 rows of width 7; those inputs stay serial and are not performance
evidence. `--reference-only --smoke` checks the independent CPython path without
LLVM or a native executable. Run timing sweeps in an otherwise quiet CPU budget.

The default workload has 8,192 rows of width 32 (262,144 input elements). It tests
a higher-cost polynomial callback and a cheap affine control. For each, the same
frozen executable supports:

| Policy | What it measures |
| --- | --- |
| `workers=0` in this runner | An ordinary explicit nested loop with direct callback calls |
| `workers=1` | The proven row thunk and owner allocation, without thread dispatch |
| `workers=2,4,8` | The same proven row computation with bounded whole-row dispatch |

The runner compares every output bit to the CPython direct-loop oracle, checks
that both expected native row thunks exist in emitted IR, and verifies unchanged
inputs. It compiles one executable and interleaves five fresh-process samples of
every policy. Each process performs a warmup and three timed batches. Construction,
warmup and full bit-witness validation are outside the kernel timer; each kernel
timer includes result allocation, dispatch, all row work and joins. No use of
Python's `sum` or unordered partial reductions changes the reference arithmetic.

The JSON records all samples and batch times, source hashes, executable hash and
size, Git state, host/affinity/quota information, process wall/CPU/maximum RSS when
`/usr/bin/time` is available, and IR/native preparation separately. Process CPU and
RSS cover construction, warmup and validation as well as the timed work, so their
scope is broader than the kernel timer. Intermediate results are atomically
checkpointed. Compare workers 1 versus N for scheduling gains; compare the direct
loop separately because generated code and callback dispatch can differ. These
results cannot be multiplied by specialization or self-build speedups from other
experiments.

## Validation and limits

Validation on Linux x86-64 with LLVM 18.1.3 and CPython 3.13.16, keeping compiler,
runtime, library and workload sources frozen at the measured implementation:

- The full native self-bootstrap passes: CPython, stage 1 and stage 2 emit identical
  compiler IR (836,028 lines) and identical runtime IR (18,805 lines).
- `make check-fast lint` passes 440 unit tests, mypy on 50 compiler source files,
  Ruff, ShellCheck, the runtime root audit and strict Clang warnings. Its 30
  parallel proof/driver unit tests include unsafe bodies, unknown
  callable targets, dynamic numeric-identity programs, library shadowing, wrong
  runtime signatures and pointer provenance, and distinct map/row thunks.
- The typed-IR verifier and `llvm-as` accept the existing map pair and the new row
  IR/library fixtures under both hosted and rebuilt native compilers. The row
  fixture pins the native runtime call site.
- Existing map and new row/fallback differential tests pass in JIT and AOT (eight
  checks under each compiler). New row tests also pass with collection on every
  program allocation (four checks under each compiler). Cases include
  empty/tiny/uneven rows, a single long row, cancellation in
  floating-point addition, signed zero, infinities, NaNs, dimension-error order,
  callback mutation and first-exception behavior.
- The native scheduler probe passes 34 map and 31 row batches, with exact disjoint
  write coverage, a synchronization barrier proving real overlap, forced partial
  thread-creation failures, row-count caps, inherited signal masks and transient
  inputs during GC. Both interrupt probes observe three joins before SIGINT ends
  the process.
- The runtime ABI/effect audit passes 646 entries and 70 exception classes.
- Full corpus IR/diagnostic comparison against #1088 covers 4,246 cases. The raw
  own-library run reports 268 differences; a separate identical-input/path control
  leaves seven intended parallel fixtures, all individually classified. One new
  direct row-import fixture changes from rejection to acceptance. The raw nonzero
  result, control's limits, exact counts and representative diffs are retained in
  [the validation report](results/README.md#validation).

The [five-sample native timing campaign](results/README.md) measures 2.69x
polynomial-row speedup at four workers; the cheap affine control gets 1.58x slower.
Full `make verify`, ThreadSanitizer and macOS remain unrun on this revision. The
corpus IR comparison does not establish complete native execution or the full GC
matrix. Bootstrap and parity ran within a shared validation budget; their elapsed
times are not performance evidence. The smoke harness verifies the measurement
path, not useful scaling. The ordinary native compilation policy and CI timing
budget are unchanged.

This is deliberately narrower than arbitrary row callbacks or shared-heap
threads. It does not yet combine #1122's generated identity guards, #1125's loop
bounds proofs, or #1106/#1118 retained external CPU buffers. Those PRs introduce
additional composition and lifetime questions. In particular, retaining an
external read-only view does not freeze writable aliases. This primitive owns a
synchronous join and accepts only ordinary Pystachy float lists under the current
single-owner runtime contract. Native async cancellation, persistent pools,
concurrent mutation, cross-row reductions and general allocating callbacks on
threads are outside its contract.
