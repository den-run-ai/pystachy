# AskMe harness on five runtimes, 2026-11-12

The typed AskMe port from one source on CPython, PyPy, mypyc, the Pystachy JIT
and a Pystachy executable, beside the reference `askme.py`. Model replies are
recorded, so the times are the harness alone. Method and reproduction are in
the [benchmark guide](../README.md); every sample is in
[2026-11-12-runtimes.json](2026-11-12-runtimes.json).

## Summary

- **Starting and finishing short runs is where the executable wins.** It starts
  in 2.3 ms against 45 ms for CPython, 106 ms for PyPy and 158 ms for
  `askme.py`, which imports `requests`. The 17-run suite takes 0.20 s against
  0.98 s for the same source on CPython (4.9 times), 2.7 s on PyPy and 2.9 s
  for `askme.py` on CPython (14 times).
- **Long runs are at CPython's level.** Over 2,001 requests the executable
  matches CPython when file scanning dominates and is 1.1 times faster when the
  controller dominates. mypyc is the fastest runtime here, 1.2 to 1.5 times
  CPython. PyPy is 1.4 to 1.6 times slower than CPython and did not reach a
  steady state in a run of this length.
- **The JIT with a warm program cache behaves like CPython**: 54 ms to start,
  within 13% of CPython on long runs. Its first launch compiles for 4.2 s.
- **With a real HTTP endpoint the transport dominates the port.** Starting
  `curl` costs about 7 ms per request on every runtime; `requests` costs about
  1 ms in `askme.py`. Past startup the executable spends 8 ms per request and
  `askme.py` 2 ms, so beyond about 26 requests the reference harness finishes
  first, whatever runs the port.
- **Memory**: the executable peaks at 5 MB on a short run (CPython 17 MB, PyPy
  123 MB) and 60 MB on a long one (CPython 43 MB, PyPy 250 MB). The collector's
  32 MiB allocation window accounts for most of the long-run figure.

## Where the executable's time goes

Callgrind on the executable, 1,001-request controller run (1.54 billion
instructions). This profile and the experiment below were taken one commit
earlier (AskMe `d85caf6`), before a one-line helper that does not affect them:

| Share | Function | What it is |
|---:|---|---|
| 28% | `eqresolve`, `skip`, `eqpair_depth`, `eqv` | Runtime equality of a `json.JSONValue` with a string, resolved through type descriptors at each comparison |
| 6.5% | `memset` | Zeroing new allocations |
| 6.4% | `json._quote` | String escaping in `json.dumps` |
| 4.6% | `pys_str_splitlines` | Line splitting in reads and searches |
| 3.2% | `pys_bytes_decode` | UTF-8 decoding of files |
| 2.0% | `sha256_hex` | The port's pure SHA-256 |

On the navigation run SHA-256 rises to 17% and line splitting to 14%. CPython
does the same work in C (`hashlib`, `str.splitlines`, the `json` accelerator),
which is why a compiled harness gains little there.

The harness rescans every recorded step on each turn to find unresolved
writes, so a 2,001-step run makes about two million step visits, each with a
few `step.get("action") == "write"` comparisons. Rewriting 17 such comparisons
to narrow the value to `str` first changed the executable's medians (5 runs
each, same machine):

| Run | As pinned | Comparisons narrowed by hand |
|---|---:|---:|
| Controller, 2,001 requests | 1,510 ms | 1,139 ms |
| Navigation, 2,001 requests | 2,162 ms | 1,787 ms |

That variant is not the pinned source and is not in the tables above; both
columns come from one earlier session, so compare them with each other. It
measures what specializing union-with-`str` equality in the compiler would be
worth to this program: 1.2 to 1.3 times.

## What this means for a fast hosted model

These runs remove the model entirely. With any network endpoint, each request
also pays a connection: neither implementation reuses one, so every call sets
up TCP and TLS again. Taking the measured costs per request, about 1 ms of
harness work plus 7 ms for `curl` in the port, and about 1 ms plus 1 ms for
`requests` in `askme.py`, a request that takes 300 ms end to end spends about
3% of that time in the port and under 1% in `askme.py`. At that point the choice of
Python runtime changes a run's wall time by a few percent at most; reusing
connections would matter more than any of the runtimes compared here. The
300 ms figure is an assumption for the arithmetic, not a measurement: no hosted
endpoint was called.

What does not shrink with a fast model is startup and footprint: 2.3 ms and one
1 MB file that links only libc, libm and libgcc, against an interpreter, the
`requests` dependency tree and 158 ms.

## Limits of these numbers

- One shared virtual machine. Long-run samples spread by about 10%, and by 25%
  in the HTTP run; treat smaller differences as noise. Short-run medians were stable within a few
  milliseconds.
- Replies are recorded and local. No model, provider or network latency is
  measured, and nothing here says how well an agent solves tasks.
- The scenarios are the port's parity scenarios and one synthetic long script,
  not a sample of real agent sessions.
- The reference harness and the port were both driven through their command
  lines; the reference needs a small driver to replace `requests.post`.
